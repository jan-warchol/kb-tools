I have used this plugin for a couple weeks. Some things worked well, but I've encountered problems, too, So in this session, I would like to discuss with you the design changes that could be made to address them ( Mostly high level). You can explore the contents of the created private knowledge base here: ~/src/jan-warchol/knowledge-base. There is also a company counterpart knowledge base, but, unfortunately, it contains information about client's code, so I cannot show it to you - if there is something that you would like me to check, I can do it on the company machine.

Below is a comprehensive list of all the issues that I've encountered.

  - General
      - When trying to understand confidential project code, I stumble upon generic patterns that I would like to document, but switching the context to private laptop is problematic - partly because reformulating the patterns takes effort, and partly because in case of any errors on my side, the verifying agent will ask questions that aren't grounded in the  example from which I came.
      - recall is not enough when it comes to learning and understanding a code base. Even understanding cards seem to be too constraining
      - Current capture based flow follows my train of thought and exploration. That's valuable but often it goes against the structure of the code, and the resulting notes are chaotic 
      - Agents often have very good suggestions and feedback on what conclusions could be drawn from my observations or what to explore and in what way - but current workflow doesn't leave opportunity for such input. Also the agent often had good suggestions for questions that would test the understanding of some subject or expand this understanding, but there is currently no place to put such suggestions (when they aren't made during a quiz session)
      - Agent guided exploration and exercises could be very helpful - not sure if this should become a different skill or how in general to give more room to the agents for his inputs 
      - I suppose one effective way of learning a project would be agent moderated exercises - e.g. what changes in application behavior when this or that variable is changed. However, I'm afraid that would take too much time.
      - I have a problem with guiding the agents to give me good questions when an understanding card appears for some topic. Sometimes I would like the agent to ask questions that broaden the scope, so that I can learn something new, adjacent to that topic being discussed, but sometimes that's definitely unwanted because it makes the whole process much longer. Also in the normal quizzing mode, when the questions are supposed to be answerable by a short phrase, the agent very frequently gives questions that cannot be answered in that way and require a full sentence to answer.
      - Basically the biggest problem is time. When I'm learning a new code base, especially in a technology that I don't know well yet, the number of questions and topics to explore explodes exponentially. Every question answered raises two more follow-ups, or a generic pattern could be extracted from a specific example. If I had unlimited time I could simply follow all of these, but that's simply impossible.
      - The current state is that I have several long capture spending reduction, several redacted notes that don't have cards created, no time to check whether the items are up to date, and several todos pointing to general concepts or patterns that I should extract.
      - Currently "verified" is overloaded: when the verification comes from the machine it means fact checking; if it comes from the human it means approval. Maybe this should be separated? However, I'm not sure if I see any cases for machine approval or human check 

  - capturing
      - Capturing usually works well - there was only one case in which the agent insisted on me re-articulating something that I had already said
      - however Capture takes too much time, especially when trying to convey relationships and flows, things that would be best represented on a diagram
      - One example of capture being too effortful: I was reviewing a merge request and I've asked the agent to give me a diagram showing the data flow and control flow of the feature that the merge request introduced. The agent produced ASCII diagrams which were very helpful and basically instead of having to go through all the code myself and dictates my way through understanding it (like I did with another merge request, when it took 4 hours in total) I had a good understanding after reading the diagrams. Now, these diagrams were agent generated so I couldn't tell him to capture them, and redictating them would take really a lot of time, especially to capture all the connections and how they were laid out.
      - Quite often the dictation contains hedges like probably or I think or maybe. All these claims are checked by the agent during verification anyway - should the qualifiers be removed at capturing phase? 
      - Going from project specific to generic has a lot of friction. After a session of understanding some specific code, I have dictation for it, and the agent can often name the patterns present there - but dictating that, together with generic examples, would take too much time. Maybe in such cases an agent generated summary or a takeaway could be admitted? The question is whether will be more beneficial to force the proper flow of always having the user to articulate everything themselves which makes for better understanding, or allowing some agents generated content which will allow to cover much more ground.

  - redaction
      - Redaction can be problematic. If the capture is substantial, and especially if it describes some flow or it is a transcription of a session during which I was was understanding how a piece of code works - I need to go through several rounds of feedback to get the agents to produce a note that is well structured and useful as reference and learning material. Usually there are too long paragraphs and the suggested note is not scannable.
      - I think the core issue with redaction may be that its input is invariably a long piece of text, because that's what dictation produces, while the ideal format for the information that the node should convey may be very different - sometimes a nested bullet list, sometimes a table, sometimes a graph. So the redacting agent would have to reverse engineer how the author would would structure and format the note if he wasn't constrained by the dictation format. 
      - Should adding paths e.g. to a diagram require articulation, or is it something that the agent can fill in?
      - How to guide the agent when redacting raw capture into a note so that the note uses a lot of structured information - tables, bullet lists, diagrams? Especially diagrams are very useful, but giving them the right shape takes a lot of guidance for the agent 

  - item relationships and lifecycle
      - Should notes and captures have a one-to-one relationship, or can a node be constructed from many captures? Or is that going too far into the Wiki  territory?
      - Sometimes related topics and up in separate captures and therefore separate notes, but there may be facts that arise from combining them. Does it mean that a card could possibly have two notes as the source?
      - Should we forbid using an item of the same type as the source? For example, making a note the source of another node? In case of captures, this is is a difficult question: when there are multiple captures covering the same topic, or perhaps several captures and some of them go out of date while others fill in and so on. Consolidating These captures can be beneficial and in that case the new capture would have other captures at as the sources. Or maybe the consolidation should only happen at the note level?
      - Should notes repeat the sources of their captures? Like the repository paths that were checked? I think this is too much duplication 
      - I think that we shouldn't require a note to have a capture for the source - for example, because something may be so simple that the initial capture is already good enough for a note (should it be promoted?) - and also the same goes for cards: I think that in some cases it would be artificial to require creating a note if I just have want to have a cards for a specific fact. Also can cards have none node sources?
      - A difficult case appeared when I've asked the agents to verify a large substantial note against recent code changes. The agent reported significant differences. Some of them were pretty mechanical like renames or data types, but some change the flow. Having to articulate all these changes myself would simply take too much time. The agent suggested running the update skill, and the result of that skill was that he updated some places in the note, but not all code changes were reflected. The challenge here was also context switching - the task against which the note has originally been written was already completed, and I've started working on something else. I realized the need for the update, but I didn't have the code loaded to my head to quickly articulate the new code.
